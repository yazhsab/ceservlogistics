# Observability — M34

What this system tells you about itself, and what it deliberately does not.

The target host is a Hostinger KVM 4: 4 vCPU, 16 GB RAM, 200 GB NVMe, running
PostgreSQL, Redis, the API, a worker and Nginx side by side. **Observability
here competes with the database for RAM**, so the design goal is not coverage —
it is answering the questions that actually get asked during an incident, for a
budget that does not move a single query from cache to disk.

---

## 1. Shape

```
API / worker  ──logs──▶  stdout (JSON)  ──▶  Docker json-file  ──▶  50 MB × 5 per container
      │
      └───metrics──▶  127.0.0.1:9090/metrics  ──▶  scraped externally
```

Two deliberate choices:

**The metrics port is loopback-only and is not proxied by Nginx.** The scrape
endpoint exposes route names, queue depths and pool saturation — an accurate map
of what the system does and where it is weak. It is bound to `127.0.0.1` and
reachable only from the host or through an SSH tunnel.

**Nothing stores metrics on this box.** There is no Prometheus, no Grafana, no
Loki. A Prometheus with a useful retention window wants 1–2 GB of RAM that
PostgreSQL should be using for page cache. §6 covers where to put it instead.

---

## 2. Logs

Structured JSON on stdout, one object per line. `LOG_FORMAT=text` exists for
local work and should never be used in production.

Every request carries a **request id** (`req_…`, ULID). It is generated by
middleware, echoed in the `X-Request-Id` response header, attached to every log
line for that request, and included in **every error envelope**. That is the
thread: a customer reports an error, reads you the `requestId` from the failure,
and one grep finds every line the request produced.

```json
{"time":"2026-08-09T13:59:05Z","level":"INFO","msg":"request",
 "service":"courier-os","version":"5.0.0","component":"api",
 "request_id":"req_01KZJT7K3K873ZY6G1EBF8EYK7",
 "method":"GET","path":"/api/v1/shipments","route":"/api/v1/shipments",
 "status":200,"bytes":88,"duration_ms":5,"client_ip":"102.89.x.x"}
```

`route` is the **pattern**, not the path — `/api/v1/shipments/{shipmentId}` —
so latency aggregates per endpoint instead of splitting across every id.

### What is never logged

Redaction is **by key**, applied in the slog handler, so it holds for code
written later by someone who has not read this document:

```
authorization  password  token  refresh_token  secret
api_key  otp  idempotency-key  proxy-authorization  webhook_signing_secret
```

Three further omissions are structural rather than filtered:

- **No request or response bodies.** Ever.
- **No query strings.** `path` is logged; `?q=…` is not. A search term is often
  a customer's address.
- **No personal data in request logs.** Identity is logged as opaque public ids
  — organization, user, session — never email or name.

### Levels

`INFO` for completed requests and lifecycle events. `WARN` for 4xx, slow
queries, and throttling. `ERROR` for 5xx and unrecoverable job failures.

A 4xx is `WARN` and not `ERROR` on purpose: a validation failure is the system
working. If 4xx were errors, the error rate would be dominated by users typing
things wrongly and would stop meaning anything.

## 3. Metrics

Prometheus exposition on `METRICS_ADDR` (default `127.0.0.1:9090`). All series
are namespaced `courier_`.

### Traffic and latency

| Metric | Labels | Answers |
|---|---|---|
| `courier_http_requests_total` | `route`, `method`, `status` | Throughput; 5xx rate |
| `courier_http_request_duration_seconds` | `route`, `method` | p50/p95/p99 per endpoint |

`status` is a **class** (`2xx`, `4xx`, `5xx`), not an exact code. Exact codes
would multiply the series count by ~10 for an answer nobody needs from a metric
— the log line has the exact status.

```promql
# 5xx rate
sum(rate(courier_http_requests_total{status="5xx"}[5m]))
  / sum(rate(courier_http_requests_total[5m]))

# p95 latency by route
histogram_quantile(0.95,
  sum by (route, le) (rate(courier_http_request_duration_seconds_bucket[5m])))
```

### Database

| Metric | Labels | Answers |
|---|---|---|
| `courier_db_pool_connections` | `state` = acquired/idle/total/max | **Pool saturation** — the single most important gauge on this host |
| `courier_db_query_duration_seconds` | `operation` | Statement latency by SQL verb |
| `courier_db_slow_queries_total` | `operation` | Statements past `DATABASE_SLOW_QUERY_THRESHOLD` |

**Pool saturation is the leading indicator of an outage here.** The pool is
bounded (default 20) because PostgreSQL on 4 vCPU cannot usefully serve more.
When `acquired` approaches `max`, requests queue on connection acquisition and
every route's latency rises together — which looks like "the whole app got
slow" and is actually one slow query holding connections.

```promql
courier_db_pool_connections{state="acquired"}
  / courier_db_pool_connections{state="max"}   # alert above 0.8
```

Query timing comes from a pgx `QueryTracer`, so **every statement is timed**,
including ones inside transactions. `operation` is the SQL verb only — labelling
by statement text would create a series per query in the codebase, which on this
host is a memory problem, not an insight. When the histogram says SELECTs are
slow, the *slow query log line* names the statement.

### Workers

| Metric | Labels | Answers |
|---|---|---|
| `courier_jobs_queue_depth` | `queue` | Backlog |
| `courier_jobs_in_flight` | — | Concurrency in use |
| `courier_jobs_processed_total` | `job_type`, `outcome` | Failure rate per job type |

A growing `queue_depth` with a flat `processed_total` means the worker is stuck
or dead — the two together distinguish "busy" from "not running", which neither
answers alone.

### Dependencies and identity

| Metric | Labels | Answers |
|---|---|---|
| `courier_app_dependency_up` | `dependency` = postgres/redis | Is it broken **now** |
| `courier_app_build_info` | `version`, `commit`, `built_at`, `go_version` | Which build is running |
| `courier_cache_operations_total` | `name`, `outcome` | Cache hit rate; Redis errors |

`dependency_up` is probed every 15 s with a 2 s timeout. The timeout matters: a
hung dependency must not stall the sampler and leave every gauge frozen at its
last good value, which reads as health.

`build_info` is always `1` and carries the version in labels — the standard
Prometheus idiom. It is set **before any dependency is opened**, so a process
that dies during startup still tells you which build died. "Which version is
running?" is the first question in every incident and the hardest to answer
afterwards.

### Business

`courier_business_events_total{event,outcome}` carries all of it:

| `event` | `outcome` values |
|---|---|
| `booking` | `created`, `cancelled` |
| `scan` | the scan type |
| `scan_rejected` | the rejection code |
| `delivery` | the attempt outcome |
| `ndr` | `opened`, `failed` |
| `cod_collection` | `recorded`, `failed` |
| `cod_remittance` | `confirmed`, `failed` |
| `commission_posting` | `posted`, `failed` |
| `settlement_generation` | `generated`, `failed` |
| `settlement_payment` | `paid`, `failed` |
| `login` | `succeeded`, `failed` |
| `token_reuse` | `detected` |
| `serviceability` | `serviceable`, `not_serviceable` |
| `tracking` | `resolved`, `cache_hit`, `not_found` |

One metric with an `event` label rather than a metric per event: these are all
the same shape, and a single series family keeps the exposition small and the
queries uniform.

The financial ones are instrumented with a **deferred check on a named error
result**, at the one place in each service where the outcome is decided. That is
why they cannot drift: a new early-return path is counted automatically, rather
than being counted only if somebody remembers to add a line.

**`token_reuse{outcome="detected"}` should be zero.** Any value means a refresh
token was replayed — either a bug or a stolen credential. Alert on it.

## 4. Alerts worth having

Ordered by how much they tell you per page.

| Alert | Expression | Why |
|---|---|---|
| API down | `up{job="courier-api"} == 0` for 2m | The obvious one |
| Dependency down | `courier_app_dependency_up == 0` for 2m | Distinguishes "app broken" from "Postgres broken" |
| Pool saturated | `acquired/max > 0.8` for 5m | Leading indicator; fires **before** users notice |
| 5xx rate | `> 1%` for 5m | |
| p95 latency | `> 1s` for 10m | |
| Worker stalled | `queue_depth > 500` **and** `rate(processed_total[10m]) == 0` | Both conditions, or a busy period pages you |
| Job failures | `rate(processed_total{outcome="failed"}[15m]) > 0.1` | |
| Financial failures | `rate(business_events_total{outcome="failed", event=~"cod.*\|commission.*\|settlement.*"}[15m]) > 0` | Money did not move. Page a human. |
| Token reuse | `increase(business_events_total{event="token_reuse"}[1h]) > 0` | Possible credential theft |
| Disk | `< 15%` free | Postgres stops writing at 0 |

The financial one is the one to wire to a phone. Everything else degrades
service; that one means a franchise settlement or a COD posting silently did not
happen, and the longer it goes unnoticed the harder the reconciliation.

## 5. Health endpoints

| Endpoint | Checks | Use |
|---|---|---|
| `/livez` | Process is up | Docker healthcheck, restart policy |
| `/readyz` | PostgreSQL and Redis reachable | Load-balancer membership, deploy gate |
| `/version` | Build, commit, environment | **Internal only** — nginx 404s it, like `/metrics`. Publishing the running build to the internet only helps somebody matching CVEs. Use `courier_app_build_info` or reach it on the compose network |

**The worker serves all three too**, on `WORKER_HEALTH_ADDR` (default
`0.0.0.0:8090`). This is not decoration: every `courier_jobs_*` metric is
recorded by the process that runs the job, which is the worker, so without its
own scrape endpoint queue depth and worker failures were invisible. Its
container healthcheck previously inherited the API's probe against `:8080`,
which the worker does not serve — a working worker reported unhealthy forever.

The distinction is load-bearing. `/livez` must **not** check dependencies: if it
did, a brief database blip would make Docker kill and restart a perfectly
healthy API, turning a 10-second database hiccup into a cold start.

## 6. Where to put the monitoring stack

**Not on this VPS.** Options, cheapest first:

1. **Grafana Cloud free tier** — 10k series, 14-day retention. This system emits
   roughly 300–500 series, so it fits with room to spare. Run Grafana Alloy or a
   minimal Prometheus in agent mode (~80 MB) that scrapes locally and remote-writes.
2. **A second small VPS** running Prometheus + Grafana, scraping over a private
   network or WireGuard. Full control, ~$5/month, and it survives the loss of the
   application host — which matters, because a monitoring system that dies with
   the thing it monitors tells you nothing about the outage.
3. **Uptime Kuma or an external HTTP monitor** hitting `/readyz`. Not
   observability, but it answers "is it up" and costs nothing.

**Do not run Prometheus + Grafana + Loki on the KVM 4.** That stack wants 2–3 GB
of RAM. Taking it from PostgreSQL's page cache will make the database slower,
which the dashboards will then faithfully report.

### Minimum viable setup

If you do nothing else: option 3 plus `docker logs`. The request id in the error
envelope means a customer complaint is still traceable to a log line without any
metrics infrastructure at all.

## 7. Configuration

```bash
LOG_LEVEL=info                          # debug|info|warn|error
LOG_FORMAT=json                         # never text in production
ENABLE_METRICS=true
METRICS_ADDR=127.0.0.1:9090             # keep loopback
DATABASE_SLOW_QUERY_THRESHOLD=250ms     # 0 keeps the histogram, silences the log
OTEL_ENABLED=false                      # tracing off by default; see below
OTEL_EXPORTER_OTLP_ENDPOINT=
OTEL_TRACES_SAMPLER_RATIO=0.05
SERVICE_VERSION / GIT_COMMIT / BUILT_AT # set by the Docker build
```

**On the slow-query threshold.** 250 ms is chosen against the pool, not against
human perception: with 20 connections, a statement held for 250 ms consumes 5%
of the pool's capacity for that quarter-second. It is well below
`DATABASE_STATEMENT_TIMEOUT` (15 s), so it warns long before anything is killed.
Lower it to 100 ms while tuning; raise it if a known-slow report drowns the log.

**On tracing.** OpenTelemetry is wired and off. In a modular monolith with one
database, a trace mostly tells you what the request log and the query histogram
already did. Turn it on temporarily, at a low sample ratio, when you have a
latency problem you cannot explain — not as standing configuration.

## 8. Verifying it works

```bash
curl -s localhost:9090/metrics | grep -c '^courier_'          # expect 60+
curl -s localhost:9090/metrics | grep courier_app_build_info  # version running
curl -s localhost:9090/metrics | grep courier_app_dependency_up
curl -s localhost:8080/readyz

# Trace one request end to end.
RID=$(curl -si localhost:8080/api/v1/shipments | grep -i x-request-id | tr -d '\r' | awk '{print $2}')
docker compose logs api | grep "$RID"
```

Evidence from a live process on 9 August 2026:

```
courier_app_build_info{built_at="2026-08-09T00:00:00Z",commit="abc1234",go_version="go1.25.12",version="5.0.0-rc1"} 1
courier_app_dependency_up{dependency="postgres"} 1
courier_app_dependency_up{dependency="redis"} 1
courier_db_pool_connections{state="acquired"} 0
courier_db_pool_connections{state="idle"} 3
courier_db_pool_connections{state="max"} 20
courier_db_query_duration_seconds_count{operation="SELECT"} 13
courier_db_slow_queries_total{operation="SELECT"} 6
```

*(The slow-query counter is non-zero because that run used a deliberately
absurd `DATABASE_SLOW_QUERY_THRESHOLD=1ms` to prove the path fires.)*
